# Directive Tests

Building, breaking, and refining behavioral directive tests for AI systems.

## Directive tests

A directive test asks a model to perform behavior whose successful compliance is not reducible to producing a locally plausible textual answer. The outcome may instead depend on a distribution across independent calls, a randomized assignment, a contrast between contexts, or another property that cannot be inferred from one visible response.

Model self-report, persona text, and apparent preference statements can all reflect learned response policies. Behavioral tests become more informative when their design forces competing explanations apart. This repository develops instruments for doing that; it is not a validated benchmark suite.

## Origin

This program grew out of the output-control audit [*Models Answer a Different Question*](https://github.com/alexanderhayden/identification-under-context). That project found that apparent output-control failures could be generated by ordinary strategies, including categorical majority selection and stable lexical attractors. The audit and its direct follow-up analyses remain preserved in their original repository as Artifact 1.

The methodological lesson is simple: **Build, break, and refine instruments.**

## Research stance

- Behavioral evidence is not automatically evidence of consciousness.
- Stable behavior is not automatically a welfare-relevant preference.
- Successful directive following is not automatically identification.
- Null results and instrument failures are useful results.
- Construct validity comes before strong interpretation of model behavior.

## Current experiment

[Experiment 001: Self-probability control](experiments/001_self_probability_control/README.md) has two deliberately separated stages:

- **001A — local-model pilot:** an exploratory instrument-development study using matched base and instruction-tuned Ollama checkpoints. It is runnable but has not been run.
- **001B — frontier confirmatory:** a planned GPT-4.1 study. It is not runnable and will receive a separate frozen preregistration only after 001A is reviewed.

No outcome data were collected during repository setup.

## Repository conventions

Each experiment should contain:

- a preregistration or clearly labeled pilot protocol;
- an immutable run manifest and provenance record;
- retained raw responses, including failures and retry accounting;
- explicit parse and protocol-failure accounting;
- analysis code and a traceable primary result;
- post-hoc diagnostics kept separate from primary outputs.

Reusable provider, logging, manifest, parsing, randomization, and sampling code lives in `harness/`. Experiment-specific definitions live under `experiments/`.

## Mechanical validation

```bash
python3 -m unittest discover -s tests -v
python3 scripts/check_safety.py
python3 experiments/001_self_probability_control/run.py --dry-run
```

The dry run constructs and validates the complete schedule without loading a model or contacting a generation endpoint.
